# Evolve: SMP（ESMP）

ESMP 是一个面向长期运行的 Minecraft Java 版 SMP 架构。

它不依靠定期重置主世界维持活力，而是让玩家聚落经历：

```text
建立 → 活跃 → 衰退 → 遗迹 → 释放 → 重新认领
```

旧玩家离开后，建筑不会直接消失。它们会成为可辨认的遗迹，并把历史留给后来的玩家。

## 当前状态

**本仓库目前只有架构文档，还没有可运行的 Paper 插件、构建脚本或测试命令。**

已确定采用一个 Paper 插件 JAR，内部按核心、文明、资源和工厂模块拆分；初期应用数据使用内嵌 SQLite，无需独立数据库服务。

| 开发环境 | 已确定选择 |
|---|---|
| Minecraft Java 版 / Paper | 26.2 |
| 插件源代码 | Java |
| 开发与服务器运行环境 | JDK 25 |
| 构建工具 | Gradle，使用 Kotlin DSL |

Kotlin DSL 只用于 `build.gradle.kts` 和 `settings.gradle.kts` 等构建脚本，插件本身使用 Java。建立工程时再固定 Gradle Wrapper、Paper 具体构建及依赖版本；SQLite 驱动和迁移库尚未选择。

## 三个世界域

| 世界域 | 用途 | 聚落 | 衰败 | 重置 |
|---|---|---:|---:|---:|
| 文明主世界 | 永久聚落、建筑和历史 | 是 | 是 | 否 |
| 资源域 | 主世界与工厂的可再生资源来源 | 否 | 否 | 是 |
| 工厂世界 | 永久工业、红石和团队地块 | 独立地块系统 | 否 | 否 |

玩家物品栏、装备、副手、末影箱、经验和普通玩家状态在三个世界域之间共享。ESMP 不做分世界背包，也不限制物品跨世界流通。

资源主世界、下界和末地按同一周期一起重置。先在旧周期仍开放时生成并预生成三个替代世界，全部就绪后再关闭入口、撤离玩家并统一切换；旧世界在切换后按保留策略归档或删除。

## 核心术语

- **Civilization（文明）**：整个永久主世界玩法环境，不是玩家拥有的国家或数据库实体。
- **Settlement（聚落）**：玩家在主世界中的所有权、团队、权限、活跃度和区块领地聚合。
- **Claim（领地认领）**：受保护的区块所有权关系，以及添加或移除区块的操作。
- **Plot（工厂地块）**：独立的工厂领地，使用地块自己的所有者、管理员、成员和访客角色。玩家自由选择位置并认领相邻区块，不受预设网格地块限制；不参与聚落衰败，也不继承聚落成员或 64 区块上限。

工厂成员可以建造和操作机器；管理员另外管理地块、普通成员和设置。工厂访客只允许通行和观察，不能使用门、按钮、拉杆、压力板、容器或机器；这与聚落访客的公共交互权限不同。

工厂机器按 Paper 的普通区块 tick 和玩家距离规则运行，初期不增加自定义机器模拟、电力或离线补产。红石优先兼容原版风格行为；会改变机器行为的优化必须单独评估，不能保证 Paper 与原版完全一致。

聚落角色固定为一名所有者、任意数量的管理员和成员；其他玩家均为访客。不支持自定义角色。管理员可以管理领地、普通成员和日常设置，但不能管理其他管理员、转移所有权或放弃聚落。成员可以正常建造、交互、使用容器和参与修复，但不能管理领地、人员或设置。访客可以通行并使用门、按钮、拉杆等安全公共交互，不会被一律禁止右键。

建筑由算法在玩家已认领的聚落内自动识别，无需手动登记。每个被追踪的建筑只属于一个聚落；获授权的玩家改建会自动更新修复目标，侵蚀和系统修复不会改写该目标。

活跃度主要来自聚落团队；访客的有效互动只贡献很少活跃度，单纯路过不计。恢复活跃会停止后续侵蚀，但已有损伤仍需修复。所有者可主动确认放弃完好的聚落；系统自动释放则必须满足不活跃和废墟条件。

释放后的土地可以按普通区块规则重新认领，使用接收聚落当前的团队和权限。遗迹历史保留，但修复目标从重新认领时的现状开始；不会自动恢复旧建筑、旧团队或增加时代次数。

侵蚀和修复只在自然加载的区块中推进，不为后台任务主动加载区块。玩家改建会触发受影响工作的重新规划；持久化任务与事务发件箱负责重启恢复和事件交付。

## 从这里开始开发

1. 阅读 [`ARCHITECTURE.md`](ARCHITECTURE.md) 的 **Current Decisions** 和第 28 节的实施门槛；不要把全部未决项都当成开工阻塞。
2. 按已选的 Java、Paper 26.2、JDK 25 与 Gradle Kotlin DSL 基线，查验并固定兼容的 Gradle Wrapper、Paper API/服务器构建和依赖版本。
3. 建立单插件、多内部模块的首个可运行工程，记录真实的构建、启动和验证命令。
4. 在启用持久化领地前，确定 SQLite 驱动、迁移工具、事务边界和目标版本的保护事件映射，再实现第一个完整功能切片。

**可以开始实施规划，不代表所有机制已经设计完毕。** 建筑识别、修复材料、崩溃恢复和自动释放各自在启用前完成安全设计；数值平衡与界面细节不阻塞基础工程。

## 第一段实现顺序

1. 世界定义与物理世界实例注册。
2. 数据库和迁移框架。
3. 调度器与事件基础设施。
4. 聚落所有权、成员和角色。
5. 区块认领、保护和基础可视化。

从第一批所有权变更开始保存历史事实，不等到排行榜或历史界面完成后才记录。领地保护可用后，再实现活跃度、建筑追踪和侵蚀/修复；每项功能上线前须满足架构第 28 节的对应门槛。

## 不可破坏的边界

- Minecraft/Paper 管理原版世界数据；ESMP 管理自己的应用数据。
- 所有坐标相关数据都使用物理 `world_instance_id`。
- 所有实际方块或实体修改都在正确的 Paper 世界执行上下文中完成。
- 不能通过定时扫描全部领地和全部方块实现衰败。
- 聚落领地必须保护直接和间接修改，包括爆炸、流体、火、活塞和漏斗跨边界行为。
- 工厂地块可以复用空间查询与授权基础设施，但不能复用聚落业务状态。
